## 三 Runtime 的触发与 Telemetry 接口

### 3.1 订阅通知

Linxuan 介绍第一种方式：Network Agent 向 Telemetry Agent 订阅某个 flow 或 link，给出相应 ID、需要监控的现象及阈值。例如：

- 链路状态发生变化，或可用容量低于关注的阈值。
- Flow 的速率低于最低要求。
- Flow 出现 **stall**：一段时间内没有传输进展，但仅凭此还不知道原因。

阈值由 Network Agent 根据自己的资源需求/预留给出，而不是由 Telemetry Agent 决定资源承诺。Linxuan 说明返回的告警应包含所需的标识和观测/阈值等信息；具体字段的口述不完整，没有在此凭代码补齐一份已达成共识的消息 schema。

KK 对其中一处返回/确认信息提出疑问：是否只是在重复订阅时已给出的内容，是否有必要，要求再核对。该段转录不够清楚，不能据此认定 KK 否定告警需要带 ID 或阈值，也不能认定双方已决定删除某个字段。

### 3.2 周期性 query

第二种方式是按一定间隔主动检查。KK 特别澄清：

- Network Agent 定期 **query Telemetry Agent**，从响应中判断是否有 deviation。
- 不是绕开 Telemetry Agent，由 Network Agent 直接去网络设备获取 measurement。
- Telemetry Agent 底层怎样测量或采集，是它自己的实现职责。

KK 将两条路径概括为：订阅后由 Telemetry Agent publication/通知，或者周期性 query-response。两种方式获得的信息进入后续 runtime 处理。

## 四 Classify、影响范围评估与去重顺序

### 4.1 Linxuan 介绍的处理链

Linxuan 介绍从告警或周期性检查进入 runtime 图后的步骤：

1. 接收并检查事件格式，进行 `classify_event`。
2. 找到哪些 links/path/flow 出现 deviation。
3. 扩展影响范围：某条链路可能同时位于其他 flow 的路径上，不能只处理最先触发告警的那个 flow。
4. 对受影响的承诺/传输进行评估，根据当前速率与剩余传输情况估计未来完成时间。
5. 进入 `triage`，决定是否需要修复、是否已经覆盖/处理过等，再选择修复动作。
6. 执行修复计划，最后 report。

讲路径示例时，Linxuan 把 A、B、C、D 说成“四条 links”，现场纠正为四个 nodes；例子的核心是某一跳异常可能影响多条路径/多个 flows。具体是哪几跳，转录不足以可靠恢复。

### 4.2 KK：同一事件不要到后面才去重

在介绍 triage 及重复通知处理时，Linxuan 提到一种情况：agent 已开始修复或已经处理了 deviation，但 Telemetry Agent 仍不断送来相同通知。

KK 确认，这是希望抑制重复 publication 的处理。他要求：

- 接收到相同事件时，应先识别重复，再继续后续步骤。
- 对同一事件，不应重复扩展全部受影响路径、重复评估各 flow 的影响，再到后面才发现已经处理过。
- 告警进入时已有 flow ID / link ID 等标识，可利用这些信息判断是否是相同对象的重复告警。
- 去重之后，再做 classify、找出受影响的 flows/paths、分析 impact 等工作。

这里应区分**重复告警事件的去重**与**对某个 commitment 是否还需要修复的业务判断**。KK 的明确反馈是前者应尽早进行；本次没有设计事件唯一键、版本、时间窗口或恢复后再次告警的完整规则，也没有在会上确认去重代码已移动到新位置。

## 五 本地修复策略：KK 的问题与边界要求

### 5.1 Extend：同一 circuit、同一速率，延长时间

Linxuan 先介绍 `extend`：保持同一 circuit 和速率，延长结束时间，让剩余数据继续传输。

这一段关于 reservation 如何允许延长的插话转录不完整，没有形成新的期限或准入规则。不能把“延长”理解成已经获准无条件越过原 deadline 或占用别人的后续预留。

### 5.2 什么才算 local repair？

KK 说，他理解的 local repair 是 **Network Agent 不需要其他 agent 介入就能完成修复**。他用 alternate link 举例：某条链路失效后，选择另一条可行链路/路径，让同一工作继续执行。

他问当前修复策略是否包含这种替换；学生方确认有 reroute 类选项。这里讨论的是保持工作继续执行的路径替代，没有决定所有拥塞都应自动 reroute。

### 5.3 Borrow：借低优先级流的资源，可能需要 scheduler 参与

KK 提出一个高低优先级 flow 的例子：两条 flow 从 A 到 B，共享拥塞资源；高优先级 flow 无法满足需求，是否能把低优先级 flow 的部分 reservation 给高优先级 flow？

他随即指出，自己不确定这种重分配应由 Network Agent 还是 scheduler 决定：

- 被借走资源的低优先级 flow，完成时间可能受到影响。
- 因而至少需要让 scheduler 知道这种影响。
- 这可能已超出“简单本地修复”的范围。

本次**没有给出最终归属或授权协议**，也没有批准 Network Agent 可不通知 scheduler 就任意牺牲另一条流的承诺。记录保留的是 KK 对跨流影响和决策边界的疑问。

### 5.4 Raise rate：如果拥塞或故障还在，增加预留有什么用？

在核对修复动作时，KK 追问第二种策略是什么。Linxuan 解释是增加 rate/reservation，前提是存在容量。

KK 的质疑聚焦于修复触发的根因：

- 如果因为链路拥塞才需要修复，原链路上可能没有余量，怎么再提高 rate？
- 如果链路已经 failed，更不能靠增加 rate 恢复传输。

因此他不理解在这些情况下怎样“increase the rate”。本次没有完整讲清“损伤已过去、后续空闲时段补偿”等更细条件，也没有决定删除提速策略；需要后续用明确的场景与容量条件回应。

### 5.5 Congestion reroute：可能造成跨流影响与级联

KK 对拥塞场景下 reroute 也持保留意见。他说，以前这类做法曾带来很多麻烦：如果只有一条 flow，情况较简单；若有其他 flows，改路由会影响它们，并可能产生 cascading effects。

这解释了为什么不能把“检测到拥塞 → 自动改路由”当成无条件正确的 local repair。这里是 KK 提出的经验和设计顾虑，会议没有测试、量化或解决这一风险。

介绍修复动作的过程有“三种还是四种”的口头核对；最终讨论覆盖 **extend、raise rate、reroute、borrow** 四类动作，但没有把四者的适用条件和顺序逐一验收。
