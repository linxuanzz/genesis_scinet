## 一 已演示的端到端探测

SB 介绍了通过 Grafana 查看指标的工作，以及如何用 perfSONAR 的 **pScheduler REST API** 调度 RTT 和吞吐量等主动测试。她讨论了在 Mininet 中把 pScheduler 部署在宿主机或选定测量节点上的方案，测量端点随测试类型和工具而定。这次演示使用的是 ESnet 的 ANL 和 ORNL 站点，SB 汇报已手动完成 RTT 和吞吐量测试并取回结果。

- 据 SB 介绍，ESnet 测试 API 的访问受站点授权限制。提交测试时指定测量端点、测试类型和工具，按需选择 TCP/UDP、IP 版本等参数。API 异步受理，返回 task 引用，随后需定位具体 run 并轮询结果。
- SB 展示的 ping/RTT 结果包括最小值、平均值、最大值和标准差。所演示的吞吐量结果需要进一步处理才能得到平均值。
- KK 区分了两种观测粒度。这里的 RTT 和吞吐量是测量端点之间的**路径级指标**。会上还提到路径容量，摘要未说明如何测得。逐链路指标仍由 Prometheus 等来源补充，例如有对应采集时的接口或队列指标。
- KK 提出，多个 workflow flow 共用同一对源、目的端点时，要弄清探测结果能归到哪条 flow。按源、目的端点关联只能得到共享的路径观测，如何区分各 flow 仍待调查。

## 二 Telemetry Agent 的异步探测方案

SB 提出由单独的 worker 处理 pScheduler 的多步调用，供 Network Agent 通过 Telemetry Agent 的 northbound API 使用。会上描述的流程如下。

1. Network Agent 发起探测，Telemetry Agent 分配 `probe_id` 供后续查询。
2. worker 向 pScheduler 提交测试，拿到 `task_id`，再定位具体的 `run URL`。拟用 InfluxDB 追踪这些标识及 probe 状态。
3. worker 轮询 run 结果，按需做归一化或平均，处理完成后将 probe 状态从 `running` 更新为 `finished`。
4. Network Agent 轮询 northbound API，完成后通过结果接口读取原始数据或处理后的结果。

会上演示的是手动 API 调用，worker、InfluxDB 状态跟踪和 northbound 结果查询仍是待讨论的集成方案。

## 三 周期探测与告警

KK 建议优先核对 pScheduler 能否直接调度重复测试，避免由 Telemetry Agent 自己维护 cron 任务。会后查阅官方文档，pScheduler 支持通过任务的 `schedule` 设置固定间隔 `repeat` 或 `repeat-cron`。SB 仍需确认目标部署上的接入方式，以及 worker 如何追踪每次 run。 [pScheduler 周期任务](https://docs.perfsonar.net/pscheduler_client_tasks.html#repeating-tasks) · [任务的 `schedule` 字段](https://docs.perfsonar.net/config_pscheduler_limits.html#jq-use-a-jq-script-to-make-a-pass-fail-decision)

告警方面，会议讨论的是由 **Network Agent 提供触发条件或阈值**，Telemetry Agent 据此生成告警。KK 强调 SB 需要与相关同事共同落实接口。具体条件的表达和告警机制仍待对齐。 [11 月 16 日组会的 Telemetry 讨论](20261116_runtime.md)
