### 1. Agent 怎样组装

- [tests/helpers.py](../../src/lib/network_agent/tests/helpers.py)：重点看 `make_net()`、`make_ctx()`。

当前调用形式可概括为（`request`、`now` 由调用方提供）：


### 4. NDT 控制接入点：最值得重点准备

- [sense.py](../../src/lib/network_agent/sense.py)：`SenseAdapter`、`MockSense`、`SenseError`。
- [schemas.py](../../src/lib/network_agent/schemas.py)：`ServiceIntent`、`ServiceState`。

这是现有设计预留的后端替换接口，目前实现为 mock，尚不代表真实 NDT 已兼容。

| Network Agent 操作 | 下游控制接口 | 语义 |
| --- | --- | --- |
| query | 不调用 SENSE 控制接口 | 根据容量观测生成 offers，不预留资源 |
| reserve | `propagate(intent, now)` | 预留资源，尚不下发配置 |
| commit | `commit(instance_id, now)` | 提交并下发配置 |
| modify | `modify(instance_id, intent, now)` | 修改带宽或时间范围 |
| release / 预留过期 | `cancel(instance_id, now)` | 释放资源 |

另有 `state(instance_id)` 查询实例状态。会前应熟悉传入 intent、返回实例 ID 和状态，以及失败时通过 `SenseError` 进入错误处理/回滚分支的方式。

会上重点确认：NDT 能否支持这种“预留后提交”的两阶段语义，现有接口如何映射到这些操作，失败和状态怎样返回。NDT agent 自己的内部图不必照搬 Network Agent 的五种操作图。

### 5. 拓扑与观测怎样对齐

- [topology.py](../../src/lib/network_agent/topology.py)：`Topology.from_dict()`、有向链路 ID。
- [telemetry.py](../../src/lib/network_agent/telemetry.py)：`TelemetrySource.link_samples()`、`MockTelemetry`。
- [schemas.py](../../src/lib/network_agent/schemas.py)：`LinkSample`。

需要对齐节点/端点/链路标识、时间及单位。内部链路容量用 Gbps，`ServiceIntent.capacity_mbps` 用整数 Mbps；时间使用带时区的 datetime。路径使用有向链路 ID，真实后端需要做对应映射。

`LinkSample.available_gbps` 的定义是“尚未扣除本 agent 自身预订的可用容量”，账本再扣自己的预订。若数据源已经扣过，需要适配，避免重复扣减。NDT 的观测通过谁提供、是否经过 Telemetry Agent，也需要会上确认。

**会前准备目标**：能带对方走通“创建 context → 编译 graph → 发送一条请求 → 返回 response”，再指出 NDT 将替换的 mock 控制和观测接口。优先把这条调用链讲清楚；placement / circuit / estimate 的算法细节可作为补充。

## Q2：为什么 `SenseAdapter` 继承 `Protocol`？

**用户问题**：SENSE adapter 为什么要继承自 protocol？

**回答**：这里的 `Protocol` 来自 Python 的 `typing`，用于声明结构化接口，与 `graphs/protocol.py` 中的五种业务操作协议不是一回事。

```python
class SenseAdapter(Protocol):
    def propagate(self, intent: ServiceIntent, now: datetime) -> ServiceState: ...
    def commit(self, instance_id: str, now: datetime) -> ServiceState: ...
    # cancel / modify / state 同理
```

它声明“能作为下游控制适配器的对象，需要提供哪些方法及其类型”。`AgentContext.sense: SenseAdapter` 因此可以接收不同实现，上层 graph 只依赖这个接口。

这是结构化类型：具体类不必显式继承 `SenseAdapter`，只要提供兼容的方法签名即可满足接口。类型检查器可据此检查兼容性；当前代码没有自动运行时接口校验，Python 也不会因为这条类型注解就在赋值时阻止不兼容对象。操作语义是否正确仍需要实现与验证。

## Q3：`SenseAdapter` 与 `MockSense` 是什么关系？

**用户问题**：SENSE adapter 和 mock SENSE 的关系是什么？

**回答**：`SenseAdapter` 是接口约定；`MockSense` 是目前用于测试和 demo 的具体实现，通过方法结构满足该接口，没有显式继承它。

`MockSense` 不是空壳：它会检查 `MockNetwork` 的容量、占用/释放模拟资源、分配 VLAN、维护服务实例状态，并支持注入失败。它不调用真实 SENSE，也不是完整的 NDT 系统。

```python
# AgentContext 声明依赖什么能力
sense: SenseAdapter

# make_ctx() 当前注入的具体对象
sense=MockSense(net, vlan_range=(3001, 3010))
```

以后可以新增满足接口的 NDT 适配器或真实 SENSE 适配器，并在创建 context 时替换对象。只要方法签名和行为语义兼容，上层 graph 可复用。

## Q4：NDT agent 需要基于当前代码怎样对接？

**用户问题**：如果要设计 NDT agent，那边的人员需要基于我现在的代码做怎样的对接吗？

**回答**：需要双方对齐接口，但不要求 NDT agent 复制我们的 graph、继承我们的具体类，或使用同样的内部实现。先明确 NDT 在这次集成中的角色。

如果 NDT 要替换目前的模拟网络后端，供 Network Agent 预留、提交、修改和释放模拟资源，可增加一个满足 `SenseAdapter` 的适配层。概念调用链为：

```text
Network Agent graph
  → ctx.sense（NDTAdapter，实现 SenseAdapter 接口）
    → NDT 自己的函数或服务 API
      → twin 中的资源与服务状态
```

`NDTAdapter` 是建议的类名，当前尚不存在。它可以位于我们这一侧，把 NDT 原生 API 转换成当前接口，因此不要求 NDT 团队直接使用我们的 Python 数据类型。适配层由谁实现，需要会上商定。

| 对接内容 | 当前代码约定 | 会上需要确认 |
| --- | --- | --- |
| 控制输入输出 | `ServiceIntent` → `ServiceState` | NDT 参数、实例 ID、状态及错误如何映射 |
| 控制生命周期 | propagate 预留，commit 提交，cancel 释放，modify 修改，state 查询 | 是否支持预留和提交分离，以及失败、重试时的状态语义 |
| 拓扑 | 节点/端点标识、有向链路 ID | NDT 拓扑怎样加载和映射 |
| 容量观测 | `TelemetrySource.link_samples()` → `LinkSample` | 观测由 NDT 直接提供，还是通过 Telemetry Agent 提供 |
| 时间与单位 | 带时区时间；内部 Gbps；intent 整数 Mbps | twin 的模拟时钟怎样对应 `now`，单位怎样换算 |
| 调用方式 | 当前进程内同步 Python 调用 | 可否直接调用；若远程调用，通信方式及异步完成怎样适配 |

当前 graph 会在控制方法返回后据返回状态继续更新账本；如果 NDT 只返回“任务已受理”，适配层不能直接把它当作“已预留/已提交”。同样，不能仅把 `propagate()` 写成无操作就宣称满足预留语义。若 NDT 没有这些能力，应共同调整交互约定。

补充精确说明：`SenseError` 会进入各操作自己的错误处理分支，并不是所有失败都回滚。例如当前 commit 失败保留 reservation，允许在有效期内重试；部分实例已经 committed 时，重试会查询状态并跳过这些实例。

如果 NDT 当前只承担规则/方案验证，例如 digital twin 验证新规则，这属于另一类输入输出接口，现有 `SenseAdapter` 并没有覆盖。应先确认本次对接是网络控制仿真、方案验证，还是两者都要，再确定接口范围。

## Q5：可以不关心 NDT 内部实现，只要求提供全部接口吗？

**用户问题**：也就是说，我可以完全不在乎他们怎么实现，但是他们得给我提供 SenseAdapter 的所有接口？

**回答**：基本正确。对接时可以不关心 NDT 内部如何实现，但需要关心接口的行为是否满足约定，而不只是函数名称和参数是否一致。

准确说，是注入 `AgentContext.sense` 的对象需要满足 `SenseAdapter` 的完整接口。NDT 团队可以直接提供兼容实现，也可以提供自己的原生 API，由双方商定负责的一方编写适配层；不要求其原生 API 也叫这些名字。

若要保持现有代码不变并支持完整流程，适配器需提供 `propagate / commit / cancel / modify / state`，并满足预留与提交分离、实例状态、错误和重试等行为约定。如果当前 demo 只走部分流程，可以先对接该路径实际使用的能力，但不能据此称为完整兼容；例如 reserve → commit → release 的路径也会用到 `state()`。

因此可以把要求表述为：“我们不限制 NDT 的内部实现；希望通过一个适配层支持这些操作，并对齐输入输出和行为语义。”

## Q6：这五个方法是 SENSE 原生 API 吗？证据是什么？

**用户问题**：propagate、commit、cancel、modify、state 是 SENSE 原生的 API 吗？给出证据。

**核对日期**：2026-11-04。直接读取 SENSE-O Northbound Intent API **2.0.4** 的原始 OpenAPI JSON，并检查官方 Python client。结论是：前四个有原生操作/端点对应，`state()` 是我们为状态查询定义的方法名；整个 `SenseAdapter` 是本项目的简化封装，不能称为五个原生 SDK 方法的直接复刻。

### 原始 API 定义证据

来源：[SENSE-O 2.0.4 原始 OpenAPI JSON](https://api.swaggerhub.com/apis/xi-yang/SENSE-O-Intent-API/2.0.4)，[Swagger UI](https://app.swaggerhub.com/apis/xi-yang/SENSE-O-Intent-API/2.0.4)。本次浏览工具无法打开 SwaggerHub 页面，但通过 Python urllib 成功取得并解析原始 JSON；以下是实际读取的路径和 schema。

| 当前 adapter 方法 | SENSE-O 2.0.4 对应 | 证据位置 |
| --- | --- | --- |
| `propagate` | `PUT /instance/{siUUID}/propagate` | `paths["/instance/{siUUID}/{action}"].put`；`components.schemas.Operation.enum` 包含 `propagate` |
| `commit` | `PUT /instance/{siUUID}/commit` | 同一通用操作端点；枚举包含 `commit` |
| `cancel` | `PUT /instance/{siUUID}/cancel` | 同一通用操作端点；枚举包含 `cancel` |
| `modify` | `POST /instance/{siUUID}/modify` | 有独立的 `paths["/instance/{siUUID}/modify"].post` 定义 |
| `state` | 状态查询可用 `GET /instance/{siUUID}/status`，另有 `/substatus` | 原生方法/端点名称是 status/substatus；`state()` 是本项目封装名 |

### 官方 Python client 交叉证据

以下链接固定到已有项目资料引用的 commit `f306b49342fd812e866c438ca353e99dee34f95a`，是交叉佐证，不宣称该 client 文件与 2.0.4 的每个字段完全一致（文件头标注生成依据为 2.0.2）。行号按实际下载的源文件计。

- [instance_api.py](https://github.com/sdn-sense/sense-o-py-client/blob/f306b49342fd812e866c438ca353e99dee34f95a/sense/client/instance_api.py)：`_allowed_actions` 包含 `propagate / commit / cancel`；`instance_operate()` 使用 `PUT /instance/{UUID}/{action}`。`instance_modify()`（第 469 行）调用 modify 端点，`instance_get_status()`（第 559 行）调用 status 端点。
- [workflow_phased_api.py](https://github.com/sdn-sense/sense-o-py-client/blob/f306b49342fd812e866c438ca353e99dee34f95a/sense/client/workflow_phased_api.py)：支持 phased workflow 的 `propagate / commit`，并将 `instance_create(intent)` 与 `instance_operate(action)` 分开。

### 对当前对接讨论的修正

1. 我们的 `propagate(intent, now)` 把更多工作合成了一次调用。原生 propagate 作用于已有 UUID；真实适配器通常还需要获取 UUID、提交 intent，再执行 propagate，并取得所需状态。
2. 原生控制端点的成功响应可以是 **204 无内容**；通用操作的 `sync` 参数默认 false。我们的方法返回的是项目自己的 `ServiceState`，所以真实适配层需要处理等待/查询、状态转换和必要字段补齐，不能把 HTTP 响应直接当作该对象。
3. OpenAPI 的 modify 定义明确不支持两阶段 modify；目前 `MockSense.modify()` 允许修改 reserved 或 committed 实例，不能仅因原生有 `/modify` 就认定所有状态下语义完全匹配。
4. 因此给 NDT 团队的准确说法是：“我们的接口参考了 SENSE 的生命周期操作，并做了简化封装；希望共同确认 NDT 与这些操作的映射。”不能说“SENSE 原生就是这五个相同签名的方法，因此 NDT 必须照抄”。

另外，较早设计笔记曾把状态读取概括为 `GET /instance/{uuid}`；本次 2.0.4 OpenAPI 核对到的明确状态端点是 `/status` 与 `/substatus`。本条以直接核对的 API 定义为准，未修改其他人工维护笔记。

## Q7：为什么需要 NDT agent，其职责是什么？

**用户问题**：为什么需要 NDT agent，其职责是什么？

**回答**：应先区分 NDT（网络数字孪生环境）与 NDT agent（管理、调用这个环境的组件）。从现有架构理解，NDT 让团队能在模拟环境中测试网络决策；NDT agent 可以让其他组件方便地使用这个环境。但单独设置一个 agent 是否必要，取决于所需功能，不能仅从名称推导出完整职责。

**已有记录确认的边界**：[2026-09-21 设计笔记](20260921_crosssitev2.md) 将 SENSE-O / NDT 放在 Network Agent 下方，提供实际或模拟网络环境；[2026-11-03 会议记录](../meetings/20261103_scinet_5verbs.md) 说明 NDT agent 的形态和接口仍需讨论。因此下列是基于当前架构的职责建议，不是会议已定稿的分工，也不代表现有 NDT 已支持这些能力。

| 建议职责 | 具体工作 | 与其他组件的边界 |
| --- | --- | --- |
| 管理模拟环境 | 初始化拓扑、重置场景、设置背景负载和故障、协调模拟时间 | NDT 执行仿真，agent 组织这些操作；具体是否支持需确认 |
| 执行网络控制请求 | 将资源预留、提交、修改和释放映射到 twin 原生操作 | Network Agent 做资源决策；NDT 侧执行并报告结果 |
| 暴露仿真结果 | 提供实例状态、容量与仿真支持的性能指标 | Telemetry Agent 可负责统一收集和提供观测；不需重复建设 telemetry 系统 |
| 组织方案验证（后续可选） | 在指定场景运行候选方案/规则，返回约定的评估结果 | 是否接受或部署规则由决策层负责；现有 SenseAdapter 未覆盖验证任务接口 |

对当前代码最直接的连接是：Network Agent 通过满足 `SenseAdapter` 的适配层控制 twin；通过 `TelemetrySource` 获得适配后的观测。NDT agent 的范围可能比这两个适配器更大，也可能当前只需很薄的调用封装，不应简单等同于 `SenseAdapter`。

如果只需把五种控制操作转给 NDT，普通 Python adapter 或 API 服务就可能足够，未必需要单独的 LLM/LangGraph agent。如果还需自动组织测试场景、协调调用其他组件并汇总验证结果，独立 NDT agent 的价值才更明确。这是架构判断，最终分工仍需双方确认。

会上最值得先确认的问题是：“你们说的 NDT agent，是让我们的 Network Agent 控制 twin 的接口，还是还负责场景管理和方案验证？”

## Q8：mock 拓扑中的链路端点是节点名，而不是接口名吗？

**用户问题**：对方询问：“in the mock network you use, the src and dst of each link is just node name, right? not interface names?” 并给出 `TOPO` 中的 nodes 和 links，询问是否正确。

**回答**：正确。当前拓扑的 `a`、`b` 是 `nodes` 中的节点 ID；`Topology` 将每条链路展开为两个有向链路时，直接用这两个节点 ID 作为 `DirectedLink.src` 和 `dst`。`TopologySpec` 还会检查端点确实属于节点集合。当前拓扑模型没有端口/接口名称字段。

例如 `L2` 连接 `esnet-atl` 与 `esnet-chi`，内部生成 `L2:esnet-atl>esnet-chi` 及反向链路，名称中的端点仍是节点 ID。对接需要具体接口/端口的 NDT 时，应另外约定映射。

可直接回复：

> Yes, that's right. In the current mock topology, `a` and `b` are node IDs, and they become `src` and `dst` for the directed links. Interface/port names are not modeled yet.

代码依据：[topology.py](../../src/lib/network_agent/topology.py) 中的 `LinkSpec`、`TopologySpec._consistent()` 和 `Topology.__init__()`。
