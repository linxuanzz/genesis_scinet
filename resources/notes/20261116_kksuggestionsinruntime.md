关键是：**入口只知道“哪个 link/flow 发来了什么告警”，还不知道“这次影响了哪些 commitment、问题是否与上次相同”。**

举个例子：

1. **第一次：L2 故障。**

Network Agent 检查发现 T1 受影响，无法修复，于是向 Scheduling Agent 上报“T1 无法完成”。此时记录 `already_reported(T1)`。
2. **随后：T2 新预约了一条经过 L2 的未来路径。**  
比如原本预计 L2 会在 T2 开始前恢复，但故障持续了。
3. **再次收到 L2 的新告警。**  
这次同样是“L2 故障”，但检查后会发现：

- **T1**：原来的问题，已经上报，可以跳过重复上报。
- **T2**：新受影响，需要处理和上报。

**如果入口看到“L2 的故障已经处理过”就丢掉整条告警，会漏掉 T2。**必须先找出受影响的 commitments，再逐个判断谁已经上报。

另一种情况是**周期检查** `Tick`：它只表示“现在检查一下”，连哪个 commitment 出问题都不知道，更无法在检查前判断是不是已经上报过。

所以：

- **同一条告警被原样重发**：可以在入口直接去重。
- **新告警/新一次检查，只是分析后发现问题没变**：需要先分析，再用 `already_reported` 抑制重复处理。

**不是任何去重都不能前移，而是当前这段判断依赖前面分析出来的结果，不能原封不动地搬过去。**

## **1.** `extend`**：延长原 circuit 的预留时间——可以保留，但不能无条件自主执行**

它解决的是：**原来的预留时间不够用了，但继续使用原路径仍然有意义。**

例如：

> 原计划 10:00 传完，中间故障停了 10 分钟。链路已经恢复，10:00–10:10 又有空闲容量，可以延长预约来完成传输。

Network Agent 可以自行执行的前提：

- 延长部分有可用容量，不挤占其他预约。
- 新完成时间在 Scheduler **允许调整的范围内**。
- 有依据认为延长后确实能完成。

需要交给 Scheduler 的情况：

- 会影响下游任务开始时间，或超过授权时间范围。
- 必须推迟其他 transfer 才能腾出时间。
- 发送端迟迟没有启动，需要调整计算任务或数据准备流程。

**不合理的用法**是：链路仍然断着、恢复时间未知，却仅靠延长预约就宣布“修复成功”。延长保留了资源，不代表恢复了传输。

当前 `extend`](/Users/lxzhong/Documents/GitHub/genesis_scinet/src/lib/network_agent/src/runtime/[repair.py](http://repair.py)) 已检查容量、预计完成时间和 `latest_finish`；**缺的是对 Scheduler 原先采用的完成时间及授权范围的约束**。

## **2.** `raise_rate`**：提高原 circuit 的预留速率——有合理用途，应该保留**

KK 的质疑适用于：**瓶颈仍然存在，实际容量不足，却想通过调高预约数字解决拥塞。**这种做法当然无效。

但下面这个情况合理：

> 之前发生短暂故障，现在链路已恢复。T1 原来预留 40 Gbps，目前可以安全提供 50 Gbps。提高到 50 Gbps，可以追回损失的时间。

代码里就有这个[测试场景 (line 107)](/Users/lxzhong/Documents/GitHub/genesis_scinet/src/lib/network_agent/tests/test_step7_repair.py:107)：

- 09:15–09:30 发生故障。
- 09:40 检查时，故障已经结束。
- 保持 40 Gbps，要到 10:15 才能完成，超过 10:10 deadline。
- 提高到 50 Gbps，可以在 10:08 完成。

因此：

- **使用未被预约的可用余量**，且在授权范围内：可以由 Network Agent 做。
- **需要降低其他 transfer 的带宽**才能提速：已经变成资源重分配，应由 Scheduler 决策。
- **当前瓶颈无法提供更高实际速率，或已确认瓶颈在发送端**：不应尝试提速。

当前实现会通过 ledger 和后端检查新增容量，因此不是直接强行超额预约。但规划阶段主要根据物理容量判断是否值得尝试，**可以进一步按当前瓶颈和可用容量过滤无效动作**。

## **3.** `reroute`**：换到另一条路径——属于 Network Agent 的核心能力，但当前执行流程需要补强**

例如：

```
原路径：A → B → C → D
故障：      B → C
新路径：A → E → F → D
```

如果新路径满足传输要求，有足够容量，不改变其他 commitment，且切换在授权范围内，那么由 Network Agent 处理很合理。

**拥塞情况下也不是一律不能 reroute。**关键是：

- 新路径是否真的避开瓶颈，而不只是表面上换了几条边。
- 新路径及共享链路有没有足够容量。
- 是否会影响其他预约。
- 是否因为观测波动而频繁来回切换。

需要 Scheduler 决策的情况包括：必须改变其他任务的资源分配、无法维持允许的完成时间，或需要改变任务执行位置。

**当前代码还有一个比“归谁管”更具体的问题：**

`reroute` (line 270)](/Users/lxzhong/Documents/GitHub/genesis_scinet/src/lib/network_agent/src/runtime/repair.py:270) 当前执行的是：

```
建立并 commit 新 circuit
→ 取消旧 circuit
→ 返回新的 binding
```

而实际数据传输切换由上层执行；测试中还要额外调用 `follow_reroutes()` 才把 flow 移过去。

所以目前只能说明**新网络资源已经配置好**，不能直接等同于**传输已经恢复**。更完整的流程应是：

```
准备新 circuit
→ 通知传输执行方切换
→ 确认切换成功
→ 释放旧 circuit
```

这里涉及的是**执行方配合切换**，不一定需要 Scheduler 重新做调度决策。如果底层后端能透明完成切换，才更符合 KK 所说的完全本地修复。

## **4.** `borrow`**：降低其他 commitment 的带宽来帮助当前传输——建议交给 Scheduler 决策**

这是四种方法里边界最明确的一项，因为它**主动修改了别人的资源承诺**。

例如：

> T1 优先级高，需要更多带宽；T2 原本预计 11:00 完成，降低 T2 带宽后预计 11:30 完成，仍早于它的 12:00 deadline。

当前代码认为，只要 T2 还能赶上 `latest_finish`，就可以借。

但这仍然可能影响：

- Scheduler 已安排的下游任务。
- 已经预约的 GPU 或计算资源。
- 其他 workflow 的执行顺序。
- Scheduler 对多个任务之间的整体取舍。

**有一个 priority 数值，不等于获得了修改低优先级承诺的权限。**事后通知也不能替代事前授权。

建议分工：

- **Network Agent**：计算可行的重分配方案，说明谁让出多少带宽、双方预计完成时间如何变化。
- **Scheduling Agent**：决定是否接受这种取舍。
- **Network Agent**：执行获批的修改。

因此建议**从自动修复策略列表中移除** `borrow`。底层修改带宽、容量检查等执行能力可以保留。未来若 Scheduler 明确授予了“哪些预约可被借用、最多借多少”的权限，再考虑受限的自动执行。

**还应该补充的，是修复条件和结果确认，而不只是增加更多动作**


| 应补充的能力        | 作用                                   |
| ------------- | ------------------------------------ |
| **明确自主修复授权**  | 规定可延迟多久、是否允许换 binding、是否允许增加资源占用     |
| **按原因选择动作**   | 故障持续时优先评估备用路径；故障恢复后考虑延长或提速；原因不明时继续诊断 |
| **修复后验证**     | 配置成功后，确认传输确实恢复、速率和进度符合预期             |
| **有限重试与及时上报** | 没有可行方案、超出权限或重试预算时交给 Scheduler，避免无限尝试 |


还要注意，当前 `unlocated` 只表示**没有定位到原因**，不能当作已经证明是主机瓶颈。现在用观测速率限制预测是一个保守模型假设，不能据此断言“只有延长能解决”。

**建议第一步先把 `borrow` 移出默认自动修复链。**其他三个动作保留，随后分别收紧适用条件；其中 `reroute` 的“切换确认后再释放旧 circuit”是需要重点补齐的执行环节。本轮尚未修改代码。

> 如果这四个方案都失败了，就汇报给scheduling agent。我没想到scheduling agent还能做什么repair？

**Scheduler 能调整的是任务安排和需求，未必还能修好网络。四种方案都失败，表示在当前端点、数据量、deadline 和可用资源约束下**没有找到可接受的网络修复方案。

如果权限和应用允许，Scheduler 仍可以：

- **推迟任务或放宽 deadline**：给传输更多时间，同时重新安排下游任务。
- **改变任务执行位置**：例如改在数据所在站点计算，减少或避免跨站传输。
- **调整工作量**：例如应用允许时使用较小数据集、降低精度；不能由 Scheduler 擅自决定。
- **暂停或取消任务**：等待网络恢复、重新提交，或报告 workflow 失败。

这些改变产生新的需求，再交给 Network Agent 检查。

**如果时间、位置、数据量都不可调整，Scheduler 也没有额外的修复能力。**上报的意义仍然是让它停止按原计划推进依赖任务，处理等待、取消或失败，而不是保证它一定能修复。
