## 三、图的形状

```
START(event) → classify_event ─无偏差─► END
                  │ 有偏差
                  ▼
                scan_path → triage ─没有可修的─► emit_reports
                              │ 有可修的
                              ▼
                            plan_local_repair → execute_repair → emit_reports → END
```

- **classify_event**：按事件刷新相关链路的观测（复用 `refresh_stale`），读取传输进度，找出偏差：哪条链路、哪段时间、哪一类（中断 / 拥塞 / 渐慢）。
- **scan_path**：列出受影响的 commitment，包括还没开始的；逐个按实际进度和受损后的速率，重算 p50 / p95 完成时间。
- **triage**（◇ policy）：每个 commitment 归为三类之一：不用动 / 可以试着修 / 来不及（at_risk）。
- **plan_local_repair**（◇ policy）：为每个"可以试着修"的 commitment 选修法（见决策 4），按 priority 排序。
- **execute_repair**：执行修法；失败的转为 at_risk。
- **emit_reports**：把 repaired / at_risk 按原因批量整理，作为图 B 的输出。

节点处理的是"一批 commitment"，图上的分支只看"还有没有要修的"，不为每个 commitment 单独分叉。◇ 两个节点先用规则实现，放在可替换的接口后面（10/14 设计：第一版不放 LLM）。

图 B 是独立的一张图（`build_runtime_graph()`），和图 A 共用同一个 `AgentContext`（账本、SENSE、commitments）。

     - **中断**：链路 observed 变为 0。
     - **拥塞**：链路某个槽 `observed < own`，即背景流量挤占了我们承诺的容量。

3. **triage 的判据**
   - 建议：对每个受影响的 commitment：
     - 剩余字节 = 总字节 − 已传；
     - 受损后的速率 = 路径上最紧那一跳分给它的速率（拥塞时多个 commitment 怎么分，见决策 5）；
     - 用 RateModel 算出 p95 完成时间（目前是 IdealRateModel，p50 = p95）。

   - 只看已 commit 的。reserved 未 commit 的预订最多活 60 秒，不在扫描范围内。

4. **本地修复用哪些手段**
   - 建议本步做两种，按顺序尝试：
     1. **原路径调整**：延长结束时间，并且/或者在未受损的时段提高速率。这和 modify 一样，换账本的 profile、改 SENSE 实例，circuit 不变。
     2. **换路径**（make-before-break）：在另一条候选路径上为剩余字节找一个放置，新建 booking 和 SENSE 实例（propagate + commit），成功之后再 cancel 旧实例、退还旧 booking。circuit 和 VLAN 会变，所以 repaired 报告里要带回新的 commitment。

     - reserve + commit 分支的"预扣 + 编译 intent + propagate + commit"。
   - 不选的做法：在图 B 里构造假请求去调用图 A 的分支。reserve 分支要求 offer 在 offer_book 里，换路径时并没有这样的 offer；而且假请求会混进幂等缓存。
   - 不在本步：多路径拆分（第 8 步）、warm circuit。

5. **priority 在哪里起作用**
   - 建议三处，由轻到重：
     1. **拥塞时怎么分**：一条链路剩下的容量不够我们所有 commitment 用时，高 priority 的先保住原速率，同 priority 的按比例分。这决定了 triage 里每个 commitment 的"受损后速率"。
     2. **修复顺序**：高 priority 的先修，先拿到备选路径和空余容量。
     3. **借用低 priority 的 slack**：高 priority 的修不好时，可以压缩低 priority 的 commitment，比如降速再延长结束时间，**前提是被压缩的那个仍能赶上它自己的 `latest_finish`**。被压缩的那个上报 repaired，带回它的新 commitment。
   - 不在本步：让低 priority 的 commitment 变成 at_risk 来保住高 priority 的（真正的抢占）。这是跨 workflow 的取舍，按 10/27 记录 2.6 节应由 scheduler 汇总决定；本步只把相关信息放进 at_risk 报告，留作 hook。
   - 第 3 处可以先不做，如果你想控制范围。

6. **上报格式与去重**
   - 建议新增两种消息（`schemas.py`）：
     - `Repaired(commitment_id, transfer_id, workflow_id, cause, links, action, commitment)`：承诺仍成立，带回更新后的 commitment；
     - `AtRisk(commitment_id, transfer_id, workflow_id, cause, links, predicted_finish_p50, predicted_finish_p95, latest_finish)`：承诺保不住，等 scheduler 决定。
     - `cause` 取值：`link_down` / `congestion` / `slow_transfer`。
   - 图 B 的输出是按 cause 分组的报告列表，**怎么送到 scheduling agent 由调用方负责**（推送通道留作 hook），测试里直接读输出。
   - 去重：每次 tick 都会重新看到同一个偏差。同一个 commitment、同一个 cause，at_risk 只报一次，直到情况变化（被修好、被 scheduler modify / release、或原因变了）。在 context 里记一本"已上报"的账。
   - at_risk 之后，network agent **不动**这个 commitment 的资源，等 scheduler 通过图 A 决定。

你说的 own（准确说是这条 transfer 的预留速率）和 **real_rate**（实际拿到的速率）比较，回答的是另一个问题。两者分工：

**5. telemetry 告警的设计**

原则沿用 10/23 定下的边界：telemetry 只懂链路和 flow，不懂 workflow / task；network agent 负责把告警对应到 commitment。建议用"**订阅 + 推送**"：network agent 告诉 telemetry 关心什么、阈值多少，telemetry 只在条件满足时推送。

需要四类告警：

| 告警 | 对象 | 触发条件 | 用途 |
|---|---|---|---|
| `link_down` / `link_up` | 链路 | 链路状态变化 | 故障，事件型，可以很快 |
| `link_capacity_below` | 链路 + 时间段 | 可用容量（不算我们的）低于订阅时给的阈值 | 拥塞；阈值 = 我们在这条链路这段时间承诺的总量，booking 变化时 network agent 更新订阅 |
| `flow_below_rate` | flow | 测得的吞吐持续低于阈值（例如低于预留的 90% 达到 N 秒） | 传输受损的主信号；必须带观测窗口，否则抖动会造成误报 |
| `flow_finished` / `flow_stalled` | flow | 传输完成，或一段时间内没有进度 | 完成通知（10/27 KK 希望用 pub/sub 尽快知道完成或失败）；停滞等同严重受损 |

每条告警的公共字段：`alert_id`、`kind`、对象（`link_id` 或 `flow_id`）、时间段 `[start, end)`、测得值、阈值、`observed_at`、`source`。订阅消息：`Subscribe(kind, 对象列表, 阈值, 最短持续时间)`。

还没定、需要和 SB 对齐的：`flow_id` 用什么（我们的 SENSE instance id、VLAN，还是五元组）；底层拿不到逐 flow 测量时怎么办（只能退回链路级）；告警恢复（如 `link_up`）要不要也推送。

本步的做法：network agent 这一侧按上面四类实现接收；mock 从模拟网络生成这些告警；同时保留定时检查（`tick`）作为兜底，以防告警丢失或底层不支持。等和 SB 对齐后，只需改接收这一层。

**6. mock 怎么算我们的流的实际速率**

这是给模拟网络用的一条规则，目的是在测试里造出"传输实际进度"，代替真实测量。一条传输在某个时刻的实际速率，受三样东西限制：

1. **不会超过我们预留的速率**：circuit 只开了这么宽。
2. **不会超过路径上最紧的那一跳还剩下的容量**：链路容量减去别人的流量；链路中断就是 0。
3. **端主机等链路以外的原因**：用一个系数模拟，正常是 1，"磁盘读得慢"就设成比如 0.6（`add_slowdown`）。

实际速率 = min(1, 2) × 3。例子（L2 容量 100，我们预留 100）：

| 情况 | 1 预留 | 2 剩余容量 | 3 系数 | 实际速率 | 对应 cause |
|---|---|---|---|---|---|
| 正常 | 100 | 100 | 1 | 100 | — |
| 别人跑了 30 | 100 | 70 | 1 | 70 | `congestion` |
| L2 中断 | 100 | 0 | 1 | 0 | `link_down` |
| 端主机慢 | 100 | 100 | 0.6 | 60 | `unlocated` |

把每段时间的实际速率乘以时长、累加起来，就是"到现在为止传了多少字节"。"一致"的意思是：三种情况都用这一条规则算进度，network agent 读进度的方式也完全一样，它不知道背后是哪种原因，只能像真实系统那样，结合链路观测去判断。

补一点：如果同一条拥塞的链路上有我们好几条流，mock 还得决定剩下的容量怎么分给它们（真实网络里取决于 QoS 是否按 circuit 生效）。建议 mock 按预留速率等比例分，这是"网络实际怎么分"；而 priority 决定的是"我们修复时让谁先拿回容量"，两者分开。

- **应传字节** = 按预留的 rate_profile 从开始积分到 now；**已传字节** = 进度。

real_rate 仍有一个用处，但它由 network agent 自己从最近两次进度算出，不是新接口：**预测未来**。累计差距说明"已经落后多少"，却不说明"问题现在还在不在"。预计完成时间 = now + 剩余字节 / 未来速率，而未来速率取决于问题是否还在：
- 最近的速率仍低于预留 → 问题还在，按最近速率（或受损链路剩下的容量）预测；
- 最近的速率已恢复 → 只需补回落后的那部分，按预留速率预测。

还有一个要注意的情况：**传输开得晚**。scheduler 可能比预留的开始时间晚才开始传，累计差距会显示"落后"，但不是网络的问题。建议应传字节从**实际开始传的时刻**算起（进度第一次大于 0 的时刻），这需要 FlowSource 能报出开始时间，mock 里一并做；真实系统里对应 telemetry 的 flow 开始事件（可与 `flow_finished` 同类）。

**2. 同意。延长可能失败，失败就要走后面的修法，都不行再惊动 scheduler**

延长失败有两种：账本在原结束时间之后没有余量（别的 commitment 已经订了那段），或者 SENSE 拒绝 modify。这时剩下的字节没有预留容量可用，即使理论上还赶得上 `latest_finish`，承诺也已经保不住，所以要继续尝试别的修法，最后还不行就 `DeviationReport(outcome=unresolved)`。

这样三档可以合并成一条规则：**为剩余字节在 [now, latest_finish] 里找一份新的预留，改动最小的优先**，依次尝试：

| 顺序 | 修法 | 改动 |
|---|---|---|
| 0 | 不用动（预计完成 ≤ 预留结束） | 无 |
| 1 | 原 circuit 延长结束时间，速率不变 | 只改时段 |
| 2 | 原 circuit 在未受损的时段提速（可同时延长） | 改速率和时段 |
| 3 | 换路径（make-before-break） | circuit、VLAN 都变 |
| 4 | 借用低 priority 的 slack（被借的仍须按时完成） | 动到别的 commitment |
| — | 都不行 | `unresolved`，等 scheduler 决定 |

每一步都要求新预留的完成时间 ≤ `latest_finish`；某一步在账本或 SENSE 上失败，就回滚这一步、试下一步。原先的"中间档"就是第 1 步能成功的情况；"超过 latest_finish"就是第 1 步不够、从第 2 步起才可能成功的情况，两者不必分开处理。第 1–4 步成功时报 `repaired`（附新 commitment，第 4 步还要给被借用的那个也报一条 `repaired`）。
